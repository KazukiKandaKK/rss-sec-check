# バックエンド(Go)の実装方針

## 適用場面

Goでバックエンドの実装を行うとき、新しいディレクトリやパッケージを作成するとき、またはDB操作・エラーハンドリングのコードを書くときに、このskillを読む。

## ディレクトリ構成:業務領域が先、層が後

clean-architectureスキル で定義した4層(Presentation/Application/Domain/Infrastructure)と、dddスキル の業務領域ごとの分割を組み合わせ、業務領域を最初の階層に、層をその内側に置く。

```
internal/
  <業務領域>/       (例: order/, user/)
    presentation/
    application/
    domain/
    infrastructure/
  shared/           (技術的な共通処理のみ)
```

業務領域を先にする理由は、dddスキル の戦略的DDDで確定した「将来特定の業務領域を独立したサービスに切り出す可能性がある」という前提に沿うため。業務領域ごとにディレクトリがまとまっていれば、切り出す際にディレクトリを1つ移動するだけで済む。層が先だと、切り出す際に複数の層のディレクトリから該当ファイルをかき集める必要が生じる。

## shared/ に置いてよいもの

`shared/`に置くのは、特定の業務領域のビジネスルールに紐づかない、技術的な共通処理(エラー型、ロギングのラッパー、汎用的なバリデーション関数など)に限る。業務ロジックやドメイン概念は、たとえ複数の業務領域で使われていても`shared/`には置かず、まずはどちらか一方の業務領域に属させ、dddスキル の境界づけられたコンテキストの判断基準に立ち返って扱う。

## エラーハンドリング

独自のエラー型は導入せず、標準の`errors`パッケージを使う。エラーのラップには`fmt.Errorf`と`%w`、エラーの判定には`errors.Is`・`errors.As`を用いる。

## DB操作:GORMを前提とする

Infrastructure層でのDB操作は、GORMを用いる。生のSQL文字列結合は行わない。SQLインジェクション対策の詳細は security-implementationスキル を参照する。

## 依存関係

Domain層で定義したインターフェースをInfrastructure層で実装し、コンストラクタ注入で繋ぐ。具体的な注入の方法は dependency-injectionスキル を参照する。
