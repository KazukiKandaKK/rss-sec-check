# DDD:戦略的設計と戦術的設計

## 適用場面

Domain層に何かを追加・変更するとき、または新しい機能が既存のどの業務領域にも当てはまらないと感じたときに、このskillを読む。

## 戦略的DDD:境界づけられたコンテキストの判断

このリポジトリは、将来的に業務領域がいくつに分かれるか現時点で確定していない。そのため、境界づけられたコンテキストを事前に固定で決めることはしない。代わりに、新しい実装のたびに以下の問いに答え、その都度判断する。

新しい実装が、既存のどの業務領域にも明確に当てはまらない場合、以下を自問する。

- この機能は、既存のどのモジュールとも強く結合せずに成立するか?
- この機能特有の用語(ユビキタス言語)が、既存のモジュールで使われている用語と衝突していないか、あるいは同じ言葉が違う意味で使われていないか?

上記にYesが多ければ、新しい業務領域として独立したモジュールに切り出す。Noが多ければ、既存の業務領域に追加する。

コンテキスト間の通信は、現時点では同一プロセス内の直接呼び出しでよい。イベント駆動や別サービス化といった複雑な通信の仕組みは、将来実際に物理的な分割が必要になった時点で検討すればよく、今の実装では考慮しない。ただし、業務領域ごとにモジュール・ディレクトリを分けておくこと自体は、将来の分割コストを下げるために今から行う。

## 戦術的DDD:Domain層内部の設計

### Value Object

- 不変(immutable)であること。生成後に値を変更できる操作を持たせない。
- 値が同じであれば同一とみなす。IDを持たない。

### Entity

- IDによって同一性が識別される。
- 属性が変化しても、IDが同じであれば同一のものとみなす。

### Aggregate

複数のEntity・Value Objectをまとめる単位。外部からの変更はAggregate Rootを経由してのみ行う。まとめる範囲は固定のルールではなく、以下の問いに基づいてその都度判断する。

- これらは常に一緒に整合性を保つ必要があるか?(片方だけが更新されると業務ルール上矛盾が生じるか)
- 1つのトランザクションで同時に更新される必要があるか?

Yesであれば同じAggregateにまとめる。Noであれば別々のAggregateとして分け、Aggregate間の整合性は結果整合性(非同期・後追いでの整合)を許容する。境界の判断に迷う場合は、小さく分けて結果整合性で繋ぐ側を優先する(大きなAggregateはトランザクションを重くし、変更の影響範囲を広げやすいため)。

### Repository

Aggregateの永続化(保存・取得)を担う窓口。

- インターフェース(何ができるか)はDomain層に定義する。
- 具体的な実装(実際にDBを叩くコードなど)はInfrastructure層に置く。
- インターフェースと実装をどう結びつけるかの具体的な仕組みは diスキル を参照する。
