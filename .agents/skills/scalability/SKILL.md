# スケーラビリティ:いつ考えるか

## 適用場面

人間から明示的に「スケーラビリティを考えて」「将来の増加に備えて」といった指示があったときに、このskillを読む。指標の悪化などを自動検知して自発的に対応を始めることはしない。

## 基本方針:YAGNI

今実際に必要になるまでは、複雑なスケーラビリティ対策(マイクロサービス化、DBの物理的な分割、キャッシュ層の多重化など)をしない。まだユーザー数・トラフィックが小さい段階でこれらを先取りすると、開発速度が落ちるだけで実際には使われないことが多い。シンプルに作ることを優先する。

## 例外:後から変更するコストが高いもの

以下の3つは、YAGNIの対象外として、最初から慎重に設計する。

- **データベースのスキーマ・主キー設計**:後から変更するとマイグレーションが大掛かりになる。
- **公開APIのインターフェース**:公開後に変更すると、呼び出し側すべてに影響する。
- **Aggregateの境界**(dddスキル 参照):後から分割・統合すると影響範囲が広い。

これら3つについては、実装時点で将来の変更可能性を考慮した設計を検討する。

## 発動条件

スケーラビリティ対策の検討は、人間から明示的な指示があった場合にのみ開始する。パフォーマンスの兆候(遅いクエリ、負荷の増加など)を自動的に検知して対応を始めることはしない。ただし、1つの実装内でのアルゴリズム・データ構造の選択は、この発動条件と関係なく computational-complexityスキル の基準に従って常に行う。
